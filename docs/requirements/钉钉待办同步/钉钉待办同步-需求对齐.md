## 一、业务术语与业务流程对齐

### 1.1 术语钉死

| 术语 | 定义 | 状态 |
|---|---|---|
| **钉钉待办** | 钉钉「待办」应用中的任务条目。字段：`taskId`、`subject`、`priority`(10/20/30/40)、`dueTime`(epoch ms)、`createdTime`(epoch ms)、`isDone`、`finishTime`(epoch ms) | ✅ 已实测 |
| **MCP 网关** | 钉钉开放的 MCP 服务端点，`streamable-http` 协议。URL 形如 `https://mcp-gw.dingtalk.com/server/<hash>?key=<secret>` | ✅ 已实测 |
| **待办角色** | `executor`(我是执行人) / `creator`(我创建的) / `participant`(我是参与人) | ✅ 已实测 |
| **sourceKey** | Mindwtr 导入子系统的身份键。同一 sourceKey 重复导入 → 跳过而非重复插入 | ✅ 已核实 `import-apply.ts:191,431` |
| **Inbox** | Mindwtr 的 GTD 收集箱。判据：`status === 'inbox'` 且无 project | ✅ 已核实 `area-filter.ts:177` |
| **reconcile** | 本方案新增的"补丁"步骤。`applyImport` 之后对已存在任务回写完成态 | ⚠️ 本方案新增概念 |
| **单向同步** | 只从钉钉流向 Mindwtr；Mindwtr 侧的状态变化不回写钉钉 | ✅ 已确认 |

### 1.2 业务流程

**当前系统流程**：Mindwtr **没有**任何消费外部 MCP 服务的能力。
- `apps/mcp-server` 是**反向**的：把 Mindwtr 暴露给 AI 工具读写（`docs/ARCHITECTURE.md:16`）
- `apps/desktop/src/components/views/settings/settings-search.ts:25` 里的 `mcp` 关键词指的是「本地 API 服务」，与本需求无关
- 既有的四类第三方导入（OmniFocus / Todoist / TickTick / Mindwtr CSV）**全部是文件导入**，走 `IMPORT_PICKER_DESCRIPTORS` 文件选择器

**目标流程**：
```
设置 → 集成 → 钉钉待办 → 点「立即同步」
  → 读 keyring 中的 MCP 地址
  → MCP tools/call: get_user_todos（分页，executor+creator，含已完成）
  → 映射为 ImportSource → applyImport（新建）
  → reconcile（对已存在任务回写完成态）
  → 单事务落库 + 刷新 store
```

## 二、现状 vs 目标

| 维度 | 现状 | 目标 |
|---|---|---|
| 外部 MCP 消费能力 | 无 | 桌面端可拉取钉钉待办 |
| 触发方式 | — | 设置页按钮，手动，**不定时** |
| 任务落点 | — | 无 project / area（出现在 Inbox 视图） |
| 幂等 | — | `taskId` → `sourceKey` → 确定性 UUID |
| 完成态 | — | 单向：钉钉完成 → Mindwtr 完成 |
| 凭证 | — | 整 URL 存 OS keyring，可在设置页更新 |

### 2.1 ⚠️ 现状核对中发现的、与直觉不符的关键事实

**事实 1：`applyImport` 对已存在任务是「整体跳过」，不是「逐字段更新」。**
`packages/core/src/import-apply.ts:431-436`：
```ts
if (existingTaskIds.has(taskId)) {
    if (deletedTaskIds.has(taskId)) skippedDeletedTaskCount += 1;
    else skippedExistingTaskCount += 1;
    return;                    // ← 一个字段都不更新
}
```
**后果**：需求「钉钉完成 → Mindwtr 完成」**不会自动发生**。必须新增 reconcile 步骤。这是本需求的核心复杂度，也是最大的实现风险点。

**事实 2：「不同步标题/截止时间」目前是「副作用」，不是「设计保证」。**
因为事实 1 的整条跳过，已存在任务的标题/截止时间**恰好**没被同步——但代码里**没有任何字段级过滤**。一旦引入 reconcile（必然要改 `status`），这个"恰好"就被打破了。
→ 因此 reconcile **必须显式限定写入字段**为 `status` / `completedAt` / `updatedAt` / `rev` / `revBy`，其余字段原样保留。

**事实 3：`idFor` 不传会退化成随机 UUID。**
`import-apply.ts:191`：`const idFor = opts.idFor ?? (() => uuidv4());`
→ 幂等完全依赖显式传入确定性 `idFor`，漏传会导致每次同步重复建任务。

**事实 4：仓库已有「post-apply 迁移」先例，但它带 provenance 守卫。**
`packages/core/src/mindwtr-csv-import.ts:1096` 是唯一的 post-apply 打补丁先例，其守卫在 `:949`：
```ts
const hasUntouchedImporterProvenance = (task) => task.rev === 1 && task.createdAt === task.updatedAt;
```
即**只对"导入后从未被编辑过"的任务做迁移**，用户改过的会被跳过并产出 warning（`:1106`）。
→ 本需求**已确认不沿用**此守卫（见 §六 Q1），理由见 §四 隐含前提。

## 二·补 实测校准（2026-09-23，真实网关）

### 完成态：默认只返回未完成 ⚠️

| 调用 | 返回 |
|---|---|
| `todoStatus: 'true'` | 全部 `finalStatusStage: 2`（已完成） |
| `todoStatus: 'false'` | 全部 `finalStatusStage: 0`（未完成） |
| **不传 `todoStatus`** | **全部 `finalStatusStage: 0`** |

**结论**：默认行为 = 只返回未完成。**必须显式拉两个桶**（`'true'` + `'false'`），否则「钉钉完成 → Mindwtr 完成」会**静默失效**——这正是 §六 Q6 预警的风险，现已证实。

`finalStatusStage` 取值：**40 条样本中仅见 `0`（未完成）与 `2`（已完成）**，无其它取值。「取消」的待办不出现在任何桶中（Q7 关闭）。

### 返回结构：扁平，无子任务层级

40 条样本的 `todoCards` 元素字段一律为
`{ taskId, subject, finalStatusStage, createdTime, dueTime, priority }`，
**无 parent / 子任务 / 层级字段**。「忽略子待办」实为 no-op（Q5 关闭）。

### 分页

两个桶在 `pageSize: 20` 下均返回 `hasMore: true` → **总量 40+，必须各自循环翻页**。

### 字段形态（必须都处理）

| 字段 | 观测到的形态 | 处理 |
|---|---|---|
| `dueTime` | `null`（常见）、`0`（早期观测）、有值 | **`null` 与 `0` 都要当作"无日期"** |
| `priority` | 取值实测见 `20` 与 `30`；**存在整个字段缺失**；同一 taskId 两次调用字段有无不一致 | 需给默认值，不可假设存在 |
| `subject` | 纯 `[图片]`、含 `[图片]\n` 前缀、含 `@xxx` 提及、含换行与 URL、**可能长达数百字** | 见下方标题规则 |
| `taskId` | 稳定字符串（如 `57501590769`） | 用作 `sourceKey` |

### 标题规则（实测驱动）

实测 `subject` 最坏情况是一条数百字的多人公告（含换行与 URL）。规则：

1. 剥离 `[图片]` 前缀
2. 取**首个非空行**作标题
3. 完整原文写入**描述**（**不含链接**，见下方说明）
4. 若清理后为空（纯 `[图片]`），**回退保留 `[图片]` 原文**

| 实测样本 | 得到的标题 |
|---|---|
| `[图片]\n同事，融通系统 里面的工单查询…` | `同事，融通系统 里面的工单查询…` |
| `[图片]` | `[图片]`（回退） |
| `@林济煜 你跟林丛对接下。…` | `@林济煜 你跟林丛对接下。…` |
| 数百字多人公告 | 首个非空行 |

### 数据噪音（已知，不处理）

样本中存在系统通知类条目，如 `taskId: 55505226429` 的 subject 为 `张晓 创建了待办`。无法通用识别，按普通待办导入。

## 四、隐含前提挖掘 ⭐

### 4-2（最高风险）「不同步标题/截止时间」是 skip 语义的副作用

- **需求方以为**：标题/截止时间被"保护"了
- **代码实际**：`import-apply.ts:431-436` 对已存在任务整体 `return`，**没有任何字段级过滤**
- **性质**：这是**偶然结果**，不是设计保证
- **风险**：本需求必须引入 reconcile 来写 `status`。一旦 reconcile 存在，"完全不碰已存在任务"这个隐含假设就被打破。若 reconcile 实现为 `{...todo, ...existing}` 之类的展开，标题/截止时间会**突然开始被远端覆盖**——而这正是需求明确不要的
- **处理**：**必须在 reconcile 中显式限定写入字段**（白名单：`status`/`completedAt`/`updatedAt`/`rev`/`revBy`），并在测试中断言 `title`/`dueDate` 未被改动

### 4-5 子待办是否真的会被返回

- **需求方以为**：钉钉待办里有子待办
- **代码实际**：**未验证**。已实测 `get_user_todos` 返回的 `todoCards` 字段为 `{priority, taskId, finalStatusStage, subject, createdTime, dueTime}`，未见子待办结构
- **性质**：数据约束，非代码保证
- **处理**：见 §六 Q5

### 4-8 CSV provenance 守卫是否该沿用

- **既有先例**：`mindwtr-csv-import.ts:949` 只对"导入后从未被编辑过"（`rev === 1 && createdAt === updatedAt`）的任务做迁移
- **冲突点**：若沿用，"你在 Mindwtr 里改过标题的任务，完成态将永远不再同步"
- **性质**：**这是两类不同性质的操作被放在一起比较**
  - CSV 守的是**容器归属**（结构性变更，与用户的本地重组直接冲突）
  - 完成态是**生命周期事实**（与标题/容器无冲突）
- **处理**：已确认**不沿用**守卫（§六 Q1）。因此 4-2 的显式字段限定是**唯一防线**

### 4-9 「钉钉侧消失」如何检测

- **机制**：同时拉「未完成」和「已完成」两个桶后，一个曾同步过的 `taskId` 若两个桶都不出现，即判定为"钉钉侧已删除/取消"
- **性质**：可检测，但**是否要据此动作是产品决策**
- **处理**：已确认**不动**（§六 Q2）

## 七、实现

阶段1 不展开技术方案。技术方案见同目录 `钉钉待办同步-设计文档.md`（阶段2 产出）。

**已知的技术方向（仅记录，不作为结论）**：
- 复用 `packages/core/src/import-apply.ts` 的导入管道，**不扩 `ImportSourceId`**（会打断两个穷尽 `Record<ImportPickerSourceId>`：`apps/desktop/src/lib/data-transfer.ts:356`、`apps/mobile/lib/data-transfer.ts:237`）
- 落库复用 `runDataTransferTransaction`（`packages/core/src/data-transfer-transaction.ts:132`）
- 不引 `@modelcontextprotocol/sdk`（服务端导向依赖，会污染 Vite bundle），手写最小 JSON-RPC 客户端
- 出站 HTTP 走 `getTauriHttpFetch()`（`apps/desktop/src/lib/tauri-http.ts:139`），CSP 无需改动
