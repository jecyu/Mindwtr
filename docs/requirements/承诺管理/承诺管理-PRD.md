# 承诺管理 PRD

> 功能名称：承诺管理（承诺卡 + P 值排序 + 一句话理由）
> 版本：v1.0（收敛版）
> 日期：2026-09-27
> 前身：[`docs/task-sort.md`](../../task-sort.md)（草稿 v2.0，已废弃）
> 使用者：个人（单用户）
> 载体：Mindwtr 桌面端（fork）

---

## 一、背景与问题

### 1.1 要解决的问题

当前用 Mindwtr 管理任务，有五个具体痛点：

| # | 痛点 | 表现 |
|---|---|---|
| P1 | **排不出来，也说不清** | 任务来了靠感觉排。事后被问"为什么先做这个"，答不上来 |
| P2 | **并行任务乱，不知道动哪个** | 手上 5 件事，不知道保哪个、降哪个、委托哪个 |
| P3 | **执行中缺刻度** | 没有里程碑和量化指标，到交付那天才发现不达预期 |
| P4 | **不复盘，估时永远不准** | 做完就完了，没有积累。下次估时还是拍脑袋 |
| P5 | **重流程导致系统变垃圾场** | 所有任务都走完整流程，琐事堆在 Inbox 里没人清 |

### 1.2 目标

让每个任务都能回答三个问题：

1. **为什么接、为什么这样排？**（对应 P1、P2）
2. **做到什么程度算完成？**（对应 P3）
3. **我估时准不准，下次怎么改？**（对应 P4）

同时给琐事一条**轻量出口**，不让它们污染主流程（对应 P5）。

### 1.3 非目标（本次不做）

- ❌ 多人协作 / 权限 / 验收人门户 —— **工具是单用户**（任务本身涉及他人，但记录的是"我在等谁"）
- ❌ AI 自动生成任务卡
- ❌ 自动冲突重排算法
- ❌ 日历 / IM 集成
- ❌ 复杂报表、个人效能看板

## 二、核心概念

### 2.1 承诺卡

**承诺卡是任务的一个可选附属评估**，回答"这个任务值不值得做、要花多大代价"。

**关键设计：承诺卡与任务来源正交。**

- 钉钉同步进来的任务 → 可以评承诺卡
- 手动创建的任务 → 可以评承诺卡
- 任何未来来源的任务 → 都可以评

承诺卡不是任务的一种"类型"，而是任务的一个**可附加的评估维度**。任务不评承诺卡也能正常使用 Mindwtr 的全部功能。

### 2.2 未评状态

**承诺卡可以不填。不填 = 未评，系统不假设任何值。**

未评的任务：
- **不参与 P 值排序**，保持在原有位置（Inbox / Next）
- 系统给出提示："有 N 个任务还没评承诺卡"

**为什么不做默认值**：默认值会直接污染排序结果，且不同方向的默认值代价不对称（详见 §3.1 字段说明）。未评状态既不虚高、也不给错误建议，且符合 Mindwtr "先收进来，再澄清" 的既有哲学。

### 2.3 P 值

**P 值 = 任务的优先级分数。** 分子是"值不值得做"，分母是"要花多大代价"。

```
P = 价值分 ÷ 复杂度点

价值分   = 大目标分 + 紧急分 + 影响分 + 可委托分
大目标分 = max(绩效分, 能力分)
紧急分   = 从硬截止派生（48h内=3 / 本周内=2 / 无硬截止=1）
复杂度点 = 基准点 × 复杂度倍数
```

P 越高越先做。

### 2.4 硬约束一票优先

P 值是算术，但现实里有"不可谈判"的东西。勾选硬约束的任务**直接锁定优先，不参与 P 值排序**。

> 例：P=2.4 的"周五必须交的外部承诺"，应该排在 P=6.0 的"写周报"前面。算术算不出这件事，只能手动锁定。

## 三、功能需求

### 3.1 承诺卡字段（9 个）

#### 字段 1–2：大目标-绩效 / 大目标-能力

| | 说明 |
|---|---|
| **作用** | 回答"这事对我自己有没有长期价值" |
| **填法** | 两个三档下拉 |
| **取值** | 直接 = 3 / 支持 = 2 / 无关 = 1 |
| **计算** | 大目标分 = max(绩效, 能力) |

**为什么必须分成两维** —— 这是整个模型最核心的设计：

绩效是**兑现**（把已有能力换成 OKR / 晋升），能力是**积累**（把经验换成可复用资产）。同一件事可能只对其中一个有用。

若合并成单一"价值分"，会**系统性地低估能力积累** —— 因为能力任务通常不急、不影响 KPI，会被绩效任务持续挤掉。分开填是强制在排序时看见这件事。

| 例子 | 绩效 | 能力 |
|---|---|---|
| Q3 复盘汇报 | 直接 (3) | 支持 (2) |
| 写周报 | 支持 (2) | 无关 (1) |
| 沉淀一套复盘模板 | 无关 (1) | 直接 (3) |

#### 字段 3：影响分

| | 说明 |
|---|---|
| **作用** | 回答"这事对外部的后果多大" |
| **填法** | 三档下拉 |
| **取值** | 重大 = 3 / 一般 = 2 / 轻微 = 1 |

**和大目标的区别**：大目标是**对你**的价值，影响是**对外部**的后果。一件事可能对你绩效无关，但对外部影响重大（如帮客户救火）。

| 例子 | 分 |
|---|---|
| 客户方案终稿 | 重大 (3) |
| 内部周会材料 | 一般 (2) |
| 整理文档 | 轻微 (1) |

#### 字段 4：可委托分

| | 说明 |
|---|---|
| **作用** | 回答"**是不是非得我做**" —— 对应痛点 P2 |
| **填法** | 三档下拉 |
| **取值** | 必须我 = 3 / 可部分委托 = 2 / 可完全委托 = 1 |

**它的独特之处**：前三个字段都在回答"这事多重要"，只有它回答"是不是非得我做"。这是**唯一能腾出时间的维度**。

- 重要 + 必须我做 → **保**
- 重要 + 可委托 → **委托**（腾时间的地方）

| 例子 | 分 |
|---|---|
| 只有我有上下文 | 必须我 (3) |
| 我搭框架、别人填 | 可部分 (2) |
| 纯执行活 | 可完全委托 (1) |

#### 字段 5：硬约束

| | 说明 |
|---|---|
| **作用** | **一票优先**，勾了直接锁定，不参与 P 值排序 |
| **填法** | 多选，**通常留空** |
| **取值** | 健康 / 家庭底线 / 合规 / 外部硬截止 / 关键路径 |
| **约束** | ⚠️ 勾选「外部硬截止」时**必须同时填写硬截止日期**（保持与紧急分自洽） |

硬约束应该是少数。如果大部分任务都勾了，排序就失效了。

#### 字段 6：基准任务

| | 说明 |
|---|---|
| **作用** | 回答"这事**相当于几个**登录功能" —— 给估时找锚点 |
| **填法** | 从基准库下拉选一个 |
| **取值** | 见 §3.5 基准库 |

**为什么要锚点**：人对绝对时间的估计很差（"这个要 3 天"），但对**相对比较**很准（"比登录功能复杂一倍"）。基准库把判断锚在已知量上。

**双重职责**：既是 P 值的**分母来源**，也是 **P50/P80 的挂靠点**（对应痛点 P4）。

**不填会怎样**：回落到任务已有的「计划投入」字段当复杂度。功能不崩，但失去基线积累 —— 痛点 P4 不解决。

#### 字段 7：复杂度倍数

| | 说明 |
|---|---|
| **作用** | 在基准之上微调 —— 基准是"典型情况"，本次可能是简化版或加码版 |
| **填法** | 三档下拉 |
| **取值** | 简单 = 0.5 / 差不多 = 1 / 复杂 = 2 |
| **计算** | 复杂度点 = 基准点 × 倍数 |

| 例子 | 倍数 | 复杂度点 |
|---|---|---|
| 只要 5 页的复盘 PPT | 0.5 | 2 × 0.5 = 1 |
| 标准复盘 | 1 | 2 × 1 = 2 |
| 还要额外做数据分析 | 2 | 2 × 2 = 4 |

#### 字段 8：目标档位

| | 说明 |
|---|---|
| **作用** | **决定投入多少**，防止所有任务都按"卓越"做 |
| **填法** | 三档下拉 |
| **取值** | 合格 / 优秀 / 卓越 |

**这是「四档标准」的使用入口。** 四档标准**本身写在任务描述里**（纯文本，不需要结构化字段），但"这次要做到哪一档"必须是明确选项 —— 否则会默认按最高标准做，然后所有任务都超时。

| 例子 | 档位 |
|---|---|
| 内部周报 | 合格（按时发、无错） |
| 给领导的复盘 | 优秀（结论先行、一次通过） |
| 要沉淀成模板的 | 卓越 |

#### 字段 9：一句话理由（生成，不是手填）

| | 说明 |
|---|---|
| **作用** | 说清"为什么这样排" —— 对应痛点 P1 |
| **生成方式** | 系统按模板生成，**用户只读不填**（可复制） |
| **存储** | 存生成快照，供复盘时回看"当时我是怎么判断的" |

**为什么必要**：排序的**可解释性**。`P=2.4` 这个数字本身没有意义，有意义的是"因为它对绩效是直接贡献、影响重大、且只有你能做，所以排在写周报前面"。

### 3.2 P 值展示

**三层信息，各司其职：**

| 层级 | 形式 | 用途 |
|---|---|---|
| 列表徽章 | `P 2.4` | 快速扫，比大小 |
| 展开拆解 | 见下方树形 | **验证算法、调试排序** |
| 一句话理由 | 文字版 | 说清"为什么这样排" |

**展开拆解示例：**

```
Q3 复盘汇报                          P 2.4
├─ 价值分 12
│   ├─ 大目标  3   绩效直接
│   ├─ 紧急    3   48h 内
│   ├─ 影响    3   重大
│   └─ 可委托  3   必须我
└─ 复杂度点 5 = 基准「Q3复盘汇报」5 × 1
```

**关键约束**：拆解视图和一句话理由是**同一份数据的两种渲染**（数值版 / 文字版）。不得实现成两套独立逻辑，否则会出现不一致。

### 3.3 一句话理由模板

**长版：**
> 因为【大目标/影响】是【】，合格/优秀/卓越线是【】；它相当于【基准任务】×【倍数】，复杂度【】点；所以我安排在【时间】，投入【精力】；若【风险】触发，就【动作】。

**短版（列表用）：**
> 我按【硬约束 + 高价值 + 低复杂度】优先，把【任务】排在【时间】，承诺【DoD】；【其他任务】已【降档/委托/延期】。

**快速终结版：**
> 该任务【5 分钟内可完成 / 不属于我职责 / 可由他人完全负责 / 不做无影响】，所以我【快速完成 / 拒绝 / 委托 / 丢弃】。

### 3.4 排序与视图

| 需求 | 说明 |
|---|---|
| 按 P 值排序 | 新增一个排序维度，可在任务列表中选用 |
| 硬约束置顶 | 勾了硬约束的任务始终排在 P 值排序之前 |
| 未评任务分区 | 未评承诺卡的任务不参与 P 排序，单独提示 |
| 优先级动作提示 | 高 P + 可委托 → 提示"可考虑委托" |

### 3.5 基准库

**作用**：为估时提供锚点，并承载 P50 / P80 基线（痛点 P4）。

**种子数据（5–10 条）：**

| 基准任务 | 复杂度点 | P50 | P80 | 合格线示例 |
|---|---|---|---|---|
| 写周报 | 1 | 0.5h | 1h | 按时发、无错 |
| 10 页汇报 PPT | 2 | 3h | 5h | 数据无错、结论清晰 |
| 登录/注册功能 | 3 | 1天 | 2天 | 主流程通、无阻塞 bug |
| 客户方案初稿 | 3 | 4h | 8h | 覆盖需求、可评审 |
| Q3 复盘汇报 | 5 | 6h | 10h | 一次通过、领导不改 |
| 小型数据迁移 | 8 | 2天 | 4天 | 数据一致、可回滚 |

**维护方式（MVP）**：可增删改。每完成一个任务，复盘时更新实际耗时与质量，基准越用越准。

### 3.6 快速终结

对应痛点 P5 —— 给琐事一条轻量出口，不让它们污染主流程。

| 情况 | 定义 | 是否进完整流程 |
|---|---|---|
| 快速完成 | 2–10 分钟内能做完 | 否，轻量记录 |
| 拒绝 | 不该你做，退回提出人 | 否，轻量记录 |
| 完全委托 | 别人负责，你不再对结果负责 | 否，轻量记录 |
| 委托但跟进 | 别人执行，你仍对结果负责 | 原任务关闭，生成跟进任务 |
| 丢弃 / 取消 | 无价值、重复、无效 | 否，轻量记录 |
| 稍后 | 现在不处理，未来可能做 | 可进待排期池 |

**轻量记录字段**：任务名称、处理类型、一句话理由（快速终结版）。**其余全部复用 Mindwtr 已有机制。**

### 4.2 派生而非存储

| 草稿 PRD 字段 | 派生方式 |
|---|---|
| 紧急分 | 从 `dueDate` 派生（48h内 / 本周内 / 无硬截止） |
| 交付状态 | 从 `checklist` 完成比 + `status` 派生 |
| 进度偏差 | 从 `checklist` 完成比派生 |

### 4.3 机制复用

| 需求 | Mindwtr 已有机制 |
|---|---|
| 里程碑 | `checklist`（阶段节点用 checklist item 表达） |
| 「等对方确认验收」 | `status = waiting` + `assignedTo` + `reviewAt` |
| 快速终结的状态流转 | `status = done/cancelled` + `cancelledAt` |
| 看板 / 列表视图 | 现有 Board / List 视图 |
| 排序偏好持久化 | 现有 settings |

> **关于「等对方确认」**：Mindwtr 的 `waiting` 状态内置文案就是 `例如：等待张三审核...`，与本需求「交付后等提出人确认」的语义完全吻合。交付后置为 `waiting`、`assignedTo` 填提出人、`reviewAt` 设对齐时间，到点自动提醒。**无需新增任何字段** —— 且这比一个事后填写的"验收结果"枚举更好：枚举是记录，`waiting + reviewAt` 是主动提醒。

## 五、与草稿 PRD 的差异

| 项 | 草稿 v2.0 | 本版 v1.0 | 原因 |
|---|---|---|---|
| 任务卡字段 | 69 | **9** | 60 个由 Mindwtr 已有字段/机制承担 |
| 大目标维度 | 4（绩效/能力/家庭/健康） | **2**（绩效/能力） | 家庭/健康性质是"不可谈判"，已由「硬约束」承担，两者重复 |
| 紧急分 | 手填三档 | **派生** | 可从 `dueDate` 算出 |
| 四档标准 | 4 个结构化字段 | **文本** | 纯文本内容，无需结构化 |
| 验收结果 | 枚举字段 | **`waiting` + `reviewAt`** | 现有机制更强（主动提醒 vs 事后记录） |
| 提出人 | 字段 | **`tags`** | 判断依据是"是否关联大目标"，已由大目标字段编码 |
| 期望类型 | 7 项多选 | **砍掉（二期候选）** | 不进任何计算；不确定其价值，二期视需要再加 |
| 一次通过率 / 返工率 | 字段 | **砍掉** | 需要"评审次数""返工工时"，个人场景无此数据 |
| 缓冲 | 任务字段 | **砍掉** | 属周级别的规划属性，层级放错了 |
| 软截止 | 字段 | **砍掉** | `dueDate`（硬截止）+ `reviewAt`（检查点）已足够 |
| 交付状态 | 字段 | **派生** | 从 checklist 完成比算出 |
| 是否知会 | 字段 | **砍掉** | 个人场景下你自己就是提出人 |
| 团队中位 | 基准库字段 | **砍掉** | 个人场景无团队数据 |

**收敛率：69 → 9，砍掉 87%。**

| 期望类型 | 若实测发现"交付前自我提醒"有价值，加回。**建议改为单选三档（要快/要好/平衡）**，而非 7 项多选 |
| 自动 P50/P80 | 从历史实际耗时自动统计 |
| 冲突自动重排建议 | 同一时间块多任务时给出建议动作 |
| 跨设备同步承诺卡 | 见 §八 已知限制 |

## 七、验收标准

1. 能对任意任务（无论来源）填写承诺卡 9 个字段，也可留空不填。
2. 未评承诺卡的任务不出现在 P 值排序中，且有明确提示。
3. 填写完整后能算出 P 值，且展开可见完整的计算拆解（分子分母各因子）。
4. 勾选硬约束的任务在排序中始终置顶，不参与 P 值比较。
5. 勾选「外部硬截止」时，未填硬截止日期则不允许勾选。
6. 列表可按 P 值排序。
7. 每个任务能生成一句话理由，长/短/快速终结三种版本。
8. 一句话理由与展开拆解的数据一致（同一数据源）。
9. 能从基准库选择基准任务，选择后自动带出复杂度点与 P50/P80。
10. 能创建、编辑、删除基准库条目，种子数据开箱可用。
11. 快速终结路径可用，关闭后保留在「已关闭」视图可搜索。
12. 承诺卡与任务来源解耦：钉钉同步的任务不自动填充承诺卡字段。

## 八、已知限制

| 限制 | 影响 | 缓解 |
|---|---|---|
| **承诺卡不跨设备同步** | 在 Mac 上评的承诺卡，手机上不可见（P 值本身可跨设备重算） | 当前主要用 PC，可接受。二期若需跨设备，有明确迁移路径 |
| **P 值不能 SQL 排序** | 需在内存中计算后排序 | 个人任务量级（几千条）无影响 |
| **基准库需手动维护** | MVP 不做自动统计 | 复盘时顺手更新，本身也是复盘动作的一部分 |

## 十、附：术语表

| 术语 | 定义 |
|---|---|
| 承诺卡 | 任务的可选附属评估，含 9 个字段 |
| 未评 | 承诺卡未填写，不参与 P 值排序 |
| P 值 | 优先级分数 = 价值分 ÷ 复杂度点 |
| 价值分 | 大目标分 + 紧急分 + 影响分 + 可委托分 |
| 大目标分 | max(绩效分, 能力分) |
| 紧急分 | 从硬截止派生：48h内=3 / 本周内=2 / 无硬截止=1 |
| 复杂度点 | 基准点 × 复杂度倍数 |
| 硬约束 | 一票优先项，勾选后不参与 P 值排序 |
| 基准任务 | 基准库中的锚点任务，提供复杂度点与 P50/P80 |
| 一句话理由 | 由承诺卡字段生成的排序解释文本 |
