## 一、业务术语与业务流程对齐

### 1.1 已对齐术语

| 术语 | 定义 | 状态 |
|---|---|---|
| P 值 | `价值分 ÷ 复杂度点`，越高越先做 | ✅ |
| 价值分 | `大目标分 + 紧急分 + 影响分 + 可委托分` | ✅ |
| 大目标分 | `max(绩效分, 能力分)`，各三档 3/2/1 | ✅ |
| 紧急分 | 从硬截止**派生**：48h内=3 / 本周内=2 / 无硬截止=1 | ✅ |
| 复杂度点 | `基准点 × 复杂度倍数`（0.5 / 1 / 2） | ✅ |
| 承诺卡 | 任务的可选附属评估，9 个字段 | ✅ |
| 未评 | 承诺卡未填写，**不参与 P 值排序** | ✅ |
| 硬约束 | 一票优先项，勾选后不参与 P 值排序 | ✅ |
| 基准库 | 锚点任务集合，提供复杂度点与 P50/P80 | ✅ |
| 一句话理由 | 由承诺卡字段生成的排序解释文本 | ✅ |

#### ⚠️ 1 —— `dueDate` 语义与需求相反（重要）

```ts
// packages/core/src/types.ts:239,242
dueDate?: string;   // ISO date string
pushCount?: number; // Tracks how many times dueDate was pushed later
```

全仓 grep `hardDeadline|softDeadline|isHardDeadline|硬截止` **零命中**。
而 `task-utils.ts:477` 主动计数：`next.pushCount = (task.pushCount ?? 0) + 1`。

**即：upstream 把 `dueDate` 设计为"可推移的软日期"并统计推移次数，与需求要的"不可谈判的硬截止"语义相反。** 需求里的"硬截止"概念在现有代码中**无任何承载**。

#### ⚠️ 3 —— `isFocusedToday` 有配额上限

```ts
// packages/core/src/focus-utils.ts:1-3
DEFAULT_FOCUS_TASK_LIMIT = 3    // 范围 1–10
```
且 `task-status.ts:145`：任务进入 done/archived 时**强制** `isFocusedToday: false`。

**影响**：PRD 把 MIT 映射到 `isFocusedToday`，但用户可能已有 3 个焦点任务，第 4 个会被拒绝。且任务完成即失去 MIT 标记。

#### ⚠️ 4 —— `reviewAt` 提醒需 4 个条件同时成立

```ts
// packages/core/src/schedule-utils.ts:51-56
function parseExplicitReminderDate(value: string | undefined | null): Date | null {
    if (!hasTimeComponent(value ?? undefined)) return null;   // ← 纯日期直接 null
    return safeParseDate(value ?? undefined);
}
// packages/core/src/date.ts:778-781
return /[T\s]\d{2}:\d{2}/.test(dateStr);   // 必须带 HH:mm
```

提醒成立需全部满足：
1. `reviewAt` **带具体时刻**（`T HH:mm`）—— 纯日期只进 Review 视图，**静默不发通知**
2. `settings.reviewAtNotificationsEnabled !== false`（`schedule-utils.ts:413`）
3. `areTaskRemindersEnabled(settings)` 总开关
4. 任务级 `suppressMindwtrReminders !== true`（`schedule-utils.ts:68`）

**这是"静默失效"**：用户设了检查点却收不到提醒，且不报错。

#### ⚠️ 8 —— `assignedTo` 是自由文本，Person 是弱关联

```ts
// packages/core/src/types.ts:235
assignedTo?: string;   // 无 personId 外键
```
`people.ts:39` 用 `getPersonNameKey(task.assignedTo) === personKey` 做**小写名字模糊匹配**。

**影响**：改名/同名会串人，无法稳定引用。

// apps/desktop/src-tauri/src/local_api.rs:4288-4304
fn valid_checklist(value: &Value) -> bool {
    value.as_array().is_some_and(|items| {
        items.iter().all(|item| {

            item.len() == 3          // ← 恰好 3 个 key，多一个即非法
                && item.get("id").is_some()

## 三、需求改动

### 3.1 目标规则

1. 任务可附加**承诺卡**（9 个字段），也可不附加。
2. 承诺卡未填写 = **未评**，不参与 P 值排序。
3. P 值 = 价值分 ÷ 复杂度点，按 P 降序排序。
4. 勾选**硬约束**的任务**物理分区置顶**，不参与 P 值比较。
5. 勾选「外部硬截止」时**必须**填写 `dueDate`。
6. 列表可按 P 值排序；展开可见完整计算拆解。
7. 一句话理由由承诺卡字段生成，与拆解视图**共用同一数据源**。
8. 基准库提供锚点任务（复杂度点 + P50/P80）。
9. 承诺卡与任务来源**正交**。
10. 快速终结路径复用现有 `done`/`archived` 状态。

### 3.2 改动范围

**包含**：
- 承诺卡 9 字段的填写、编辑、存储
- P 值计算与未评处理
- 按 P 值排序（新增排序维度）
- 硬约束物理分区置顶
- 一句话理由生成（长版/短版/快速终结版）
- 展开拆解视图
- 基准库（种子数据 + 增删改）

**不包含**（逐条附隐含前提挖掘，见 §3.3）：
- 自动计算 P50/P80
- 冲突自动重排建议
- 验收人只读视图
- 跨设备同步承诺卡
- 期望类型字段
- 一次通过率 / 返工率 / 缓冲 / 软截止 / 提出人 / 是否知会

### 3.3 「不包含」的隐含前提挖掘 ⭐

> 方法：对每个「不包含 X」，回代码找「X 是怎么被排除的」。找到显式判断 = 真排除；靠数据/配置 = 隐含前提；都没有 = 真漏洞。

| 不包含项 | 它是怎么被排除的 | 结论 |
|---|---|---|
| 自动计算 P50/P80 | 无相关代码，MVP 主动不做 | ✅ 真排除（需求决定） |
| 跨设备同步承诺卡 | `sync-normalization.ts` 只覆盖 `tasks/sections/projects/people/areas` 五个实体，**`settings` 不在其中**；承诺卡若走 fork 私有表则天然不同步 | ✅ 真排除（结构决定） |
| 验收人只读视图 | 无相关代码 | ✅ 真排除（需求决定） |
| **期望类型** | 无字段、无代码 | ⚠️ 真排除，但**需确认**是否二期加回 |
| **一次通过率 / 返工率** | 无字段、无代码；且个人场景**无数据源**（需"评审次数""返工工时"） | ✅ 真排除（数据约束） |
| **缓冲** | 无字段 | ⚠️ 需求认为属"周级别"属性，但**周级别规划在 Mindwtr 中无载体** |
| **软截止** | 无字段；但 `dueDate` 本身就是软语义（见 §2.1 ⚠️1） | ⚠️ **需重新审视** —— 见 Q3 |
| **提出人** | 用 `tags` 承载 | ⚠️ `tags` 前缀非强制（`types.ts:243`），程序写入不带 `@`/`#` 会分类失效 |
| **是否知会** | 无字段 | ✅ 真排除（个人场景你自己就是提出人） |

**最需要重新审视的是「软截止」**：需求排除它的理由是"`dueDate` = 硬截止，`reviewAt` = 检查点，两个日期够了"。但代码事实是 `dueDate` **本身就是软语义**（有 `pushCount` 计数）。所以现状是：
- 需求的"硬截止"概念 **无载体**
- 需求的"软截止"概念 **恰好就是现有 `dueDate`**

**这是一个语义错位，必须澄清（Q3）。**

### 4.1 命名雷区（新发现）

**"commitment" 这个词在现有代码中已被占用两次，语义完全不同：**

| 位置 | 含义 | 证据 |
|---|---|---|
| `store-tasks.ts:980` | `logInfo('Commitment cancellation saved')`，`releaseCheck: 'v1.3.0/commitment-cancelled'` | 指**被取消的任务** |
