## 1. 背景与目标

### 1.1 目标

给 Mindwtr 增加**承诺管理**能力：让每个任务能回答"为什么接、为什么这样排"，并支持全局优先级排序。

## 2. 范围对齐

### 2.1 承诺管理是什么

**两个正交组成部分**，不是一个新列表：

| 组成 | 本质 | 落点 |
|---|---|---|
| **承诺卡** | 任务的一个可选评估（10 字段） | 任务编辑器里的一个面板 |
| **按 P 值排序** | 一种排序维度 | 排序下拉框里的一项 |

**正交性**：任务评了承诺卡，**仍留在原位置**（Inbox 的还在 Inbox）。承诺卡不改变任务归属。

### 2.2 术语

| 术语 | 定义 |
|---|---|
| P 值 | `价值分 ÷ 复杂度点` |
| 价值分 | `大目标分 + 紧急分 + 影响分 + 可委托分` |
| 大目标分 | `max(绩效分, 能力分)` |
| 紧急分 | 从 `dueDate` 派生：48h内=3 / 本周内=2 / 无硬截止=1 |
| 复杂度点 | `基准点 × 复杂度倍数` |
| 未评 | 承诺卡未填写 → 不参与 P 值排序 |
| 硬约束 | 一票优先项 → 物理分区置顶 |

### 2.3 范围

**包含**：承诺卡 10 字段、P 值计算、按 P 排序、硬约束置顶、一句话理由、拆解视图、基准库、里程碑、「今天」徽章。

**不包含**：自动 P50/P80、冲突自动重排、验收人视图、跨设备同步承诺卡、期望类型、一次通过率/返工率/缓冲/软截止/提出人/是否知会。

    const due = safeParseDueDate(task.dueDate)?.getTime();
    const start = safeParseDate(task.startTime)?.getTime();
    const startsToday = start !== undefined && start >= startOfTodayMs && start <= endOfTodayMs;

}

## 4. 目标规则与算法

### 4.1 P 值算法

```
P = 价值分 ÷ 复杂度点

价值分   = 大目标分 + 紧急分 + 影响分 + 可委托分
大目标分 = max(绩效分, 能力分)
紧急分   = deriveUrgency(task.dueDate, now)
复杂度点 = benchmark.points × multiplier
```

**边界**：`complexity <= 0` 时返回 `null`（不参与排序），避免除零。

### 4.2 手算验证

设 `now = 2026-09-27 10:00`：

| 任务 | 绩效 | 能力 | 大目标 | 截止 | 紧急 | 影响 | 可委托 | 价值分 | 基准 | 倍数 | 复杂度 | **P** |
|---|---|---|---|---|---|---|---|---|---|---|---|---|
| 写周报 | 2 | 1 | 2 | 今天 18:00 | 3 | 1 | 1 | **7** | 写周报(1) | 1 | 1 | **7.00** |
| Q3 复盘汇报 | 3 | 2 | 3 | 09-29 12:00（50h） | 2 | 3 | 3 | **11** | Q3复盘(5) | 1 | 5 | **2.20** |
| 客户方案初稿 | 3 | 1 | 3 | 10-02 18:00（128h） | 2 | 3 | 2 | **10** | 客户方案(3) | 1 | 3 | **3.33** |
| 沉淀复盘模板 | 1 | 3 | 3 | 无 | 1 | 1 | 3 | **8** | 10页PPT(2) | 2 | 4 | **2.00** |

**排序结果**：写周报 7.00 → 客户方案 3.33 → 沉淀模板 2.00，Q3 复盘汇报因硬约束置顶。

> 注意「写周报」P 值最高 —— 因为分母小（1 点）。这是公式的固有性质，不是 bug。
> 副作用是"重要的长任务永远排在后面"。已在原型里标注，列入 §9 待定。

### 4.3 分区算法

```ts
function partitionByCommitment(tasks, cards, benchmarks, now, defaultOrder) {
  const pinned  = tasks.filter(t => hasHardConstraint(cards[t.id]));
  const rated   = tasks.filter(t => cards[t.id] && !hasHardConstraint(cards[t.id]))
                       .sort((a, b) => score(b).p - score(a).p);
  const unrated = tasks.filter(t => !cards[t.id]);   // ← 保持传入顺序，不重排
  return { pinned, rated, unrated };
}
```

**三条规则**：
1. **硬约束**：物理分区置顶，**不参与 P 比较**（互斥过滤，不重复出现）
2. **已评**：按 P 降序
3. **未评**：保持 `default` 排序结果（`sortTasks` 的输出），**不走 `byId()` 兜底**

### 4.4 一句话理由生成

三个模板（长版/短版/快速终结版），**与拆解视图共用同一份 `CommitmentScore` 数据**，不得实现成两套逻辑。

## 5. 技术方案

### 5.1 方案选型对比

| 方案 | 承诺卡存储 | 改 `Task`? | 碰同步管线? | 合并痛苦 | 结论 |
|---|---|---|---|---|---|
| **A** | `Task` 字段 + 云同步 | ✅ 10 字段 | ✅ | 高 | ❌ 触发 6 处代码 + CI + CloudKit gate |
| **B** | `Task` 字段，仅本地 | ✅ | 需剥离逻辑 | 中 | ❌ 剥离逻辑仍要碰 `sync-normalization` |
| **C1** | `settings` JSON blob | ✅（settings 接口） | ❌ | 低 | ⚠️ key 类型受 `AppData['settings']` 约束 |
| **C2** | **fork 私有表** | ❌ | ❌ | **低** | ✅ **选定** |

**选 C2 的理由**：
1. **零 `types.ts` 改动**（TS 类型定义在自己的文件里）
2. **零同步管线改动**
3. 表结构 100% 归 fork，upstream 永不碰
4. 沿用 upstream 自己的模式 —— `calendar_sync`（`sqlite-schema.ts:155`）
5. `CREATE TABLE IF NOT EXISTS` 幂等 → **不需要写 migration**
