# Android native development app

This isolated Compose app uses `tech.dongdongbh.mindwtr.nativeclient.dev` and its own private `mindwtr-native-dev.db`. It does not read or replace the React Native app. It has three tabs, **Inbox**, **Focus**, and **Projects**. Each list shows its first 50 rows, loads more in windows of at most 50, and calls the shared core contract to capture, complete, and edit tasks. The app has no sync, external intents, fixture seeding, or production upgrade path.

Every word on screen comes from core. At boot the app calls core's `setLanguage` with the React Native app's saved language (AsyncStorage `mindwtr-language`, read by the upgrade build's guard; none in the dev build) and the device locale, then reads one label map through `getStrings`. The keys are the ones mobile uses for the same controls (`Labels.kt`). Core fills in English for a key a language lacks; a key core does not know shows as the key and is logged once. Core has no key for "Refresh", "Load more", "Reload", or "Storage unavailable", so the app uses **Try again** (`common.retry`) for a failed read and for the editor's reload, **More** (`common.more`) for the next window, and shows a failed boot as its message alone.

The app looks like the React Native app, so an RN user recognizes it at once: RN's header, RN's bottom tab bar (Focus, Inbox, the center capture button, Projects in the quick-access slot, and an empty slot where Menu goes), RN's theme tokens (`Theme.kt`, the only file with colors), RN's lucide icons (`Icons.kt`), and RN's task row (`TaskRowView.kt`). A row shows core's meta line as core sent it (project or area dot, contexts, the due date in the user's format and core's urgency color, the checklist count; detail parts stay hidden, as in RN's lists and default Focus), core's priority strip, and core's TalkBack label. A swipe right reveals RN's labelled action button for the row's status (Done, Next, or Restore, from core's row meta): a tap runs it and a long-press opens RN's status menu, as in RN. TalkBack has the same action and Change Status as custom actions; there is no Done button, as in RN. The Inbox shows RN's status glyph and a project shows RN's status badge; a tap opens RN's status menu, which saves through core's `updateTask`. The header's left side is RN's area switcher (`AreaSwitcher.kt`): core's `getAreaFilter` label, and RN's sheet, where a tap sends core's `next` selection through `setAreaFilter`. A refused star shows core's text in RN's toast. The capture button opens RN's capture popup (`CaptureScreen.kt`) on core's quick capture contract (`native-host-contract-quick-capture.ts`): Add Task and Close, the field with core's live preview, the project or contexts chip with Focus and More, More's panel (the note, the Focus, due time, contexts, area, project and priority chips with RN's pickers, the syntax help, and Today, Tomorrow, Next week and Custom; the Custom date and due time pickers open on core's day and time), and RN's Add another switch (RN's Android switch: a raised thumb on a faint track; kept on the device under RN's key) with Save & edit and Save. Every chip and picker row sends the edit core put on it. Several lines ask core's question; Create tasks writes core's recovery snapshot under `files/snapshots` (as mobile does: a temporary file, a clash number, the 5 newest) and then one task per line in one write; the batch sends the name actually written, which is on disk with the request, so a retry sends the same snapshot and a stale one is replaced with a new snapshot and the same capture UUIDs. Each save's exact request (a capture UUID, one per line for several lines) is written to a synced file in the no-backup folder before the call; a failed one keeps its exact retry, and after process death it is sent again before anything else, so core writes it once. A refused date command shows core's notice and keeps the draft. The popup's draft (text, options, open picker, and chip edits not yet answered) survives rotation and process death; a request whose outcome was lost comes back even after a force-stop. Close discards the draft, as RN does. In portrait only More's panel scrolls, as in RN; in landscape everything under the header scrolls, so Save & edit and Save stay reachable above the keyboard. RN's microphone and Import .txt are not built. The theme is RN's choice as core resolves it: the synced `settings.theme`, else RN's device-local `@mindwtr_theme` (read by the upgrade build's guard), else the system's light or dark mode.

Each screen scrolls as one list, so landscape shows rows rather than fixed controls. The Inbox's first item is RN's **Process Inbox (N)** button (core's Inbox count, shown as 99+ above 99; TalkBack hears the exact count) with RN's "All areas" line under it; an empty Inbox has no button. Only the header, the tabs, and a failure message with its retry stay fixed.

The header's search button opens RN's global search on core's `searchTasks`: the field, Clear, RN's filter sheet (due date, location, contexts and tags, Include, status, scope, area, all core's words and choices), the active chips that clear a filter, core's truncation and hidden-matches lines, and the project and task results with core's highlights and date line. A task opens the editor over the search; a result core cannot open there goes to its list when this app has it (Inbox, Focus, or a project). Such a result whose list is not built yet (Done, Archived, Waiting, Someday, Reference) keeps RN's row look without a tap or chevron until those Menu screens exist. Clearing an active chip removes its filter value, so a second tap changes nothing. Mark Done is the lists' Done. Save Search saves through core's `saveSearch`: the submitted query, name and request UUID are kept with the screen before the call, the dialog stays locked to them until core answers, and after process death they are sent again before it unlocks. The saved-search screens are not built. An answer for an older query is dropped by core's echoed query.

**Process Inbox (N)** opens RN's step flow on core's session (`startInboxProcessing`, `getInboxProcessingStep`, `commitInboxProcessingStep`, `skipInboxProcessingTask`, `endInboxProcessing`): the progress header with Close, RN's guided/quick switch (kept on the device under RN's key `mindwtr:view:inboxProcessingMode:v1`) and Skip; the item's card with its editable title and note; then core's step, drawn from core's view, where every chip, date, and suggestion sends the exact edit core put on it, one at a time. Each answer (a choice, File it, Back, Skip) is a command with a request UUID: it is written to a synced file in the no-backup folder before the call, a failed one keeps its exact retry through rotation and a new screen. After process death the app lands on the Inbox, as RN does, and the owed answer is sent again in the background: core's session died with the process, so core refuses it without writing and its message shows. The record on disk goes only after core acknowledges or refuses the answer, so another death during that replay finds it again. Core refuses a new session while earlier writes are unsaved; its message shows. The failure message is drawn above the list and is a live region, so TalkBack always reaches it.

From the repository root:

```sh
bun install --frozen-lockfile
node apps/android-native/scripts/build-bundle.mjs
cd apps/android-native/android
./gradlew :app:assembleDebug --offline
```

The build also regenerates `core-host.js` from current core source. Install only the resulting development APK (`android/app/build/outputs/apk/debug/app-debug.apk`) into the isolated development package. A clean install creates an app-private SQLite checkpoint before core schema setup. On later launches, the first checkpoint is retained. The checkpoint file and its directory entry are synced before task writes. Every core data load is checked against storage row counts, including the load during contract activation. A failed check shows only the failure message and offers no command. A capture that fails keeps its draft locked to its exact retry (the same capture UUID).

The checkpoint is a SQLite `VACUUM INTO` snapshot, so it includes committed WAL content. This development app has no other recoverable user data yet. It is not a tester build: its log is only in logcat, and it has no Settings › Diagnostics. A tester build needs that diagnostics screen, upgrade and recovery validation, and the remaining workflows before distribution.

The adapter rejects detected concurrent database writes, so the process owns exactly one core host (`ProcessCoreHost`). Activities and the Inbox `ViewModel` never close it; process death is the only shutdown. Screen state lives in the `ViewModel`, so rotation keeps an in-flight or failed save. A failed command's exact retry also stays with the process host until that retry succeeds, so a screen that is closed and reopened in the same process shows the failure and its retry again. The capture popup's draft survives process death on disk, and a capture whose outcome was lost is sent again with its capture UUID, so it is written once. `am force-stop` discards that saved screen state by Android design, but an owed capture on disk still comes back and is sent again.

Tapping a row opens the React Native task editor's Form tab. It reads core's `getTaskEditorModel` (the draft, the fields to show by section in the user's order, which sections start open, their filled counts, and every list a control picks from) and saves through core's `saveTaskDraft`; Kotlin holds no task rules. The header has RN's Close and Save; the title, then core's fields with RN's controls: status chips, the Destination picker (project or area), the section picker, the Someday section chips, the date rows (a date, or a date and a time from the clock button), context and tag fields with core's suggestions and quick chips (`getTaskEditorSuggestions`), priority, energy and time-estimate chips, the recurrence rule and "Repeat after completion", Skip reminders, assigned person, location, and notes. Every control's edit goes to core's `editTaskDraft`, one at a time, and the editor then shows the model core returns for the edited draft: its fields, sections and choices follow the draft as the user edits it. Dates show core's labels in the user's settings; a picked day keeps an existing time, the time picker starts at core's time for the field, and RN's quick date chips, Date only, the starts-after-due warning, the relative start (core moves it with the due date), the recurrence interval, days and ends, the repeat reminder intervals, and the custom time estimate all write core's values. Kotlin only turns the picker's day and time into `yyyy-MM-dd` and `HH:mm`, and core's picker start back into the picker. Typed text (title, notes, location) stays in the editor until Save. The checklist, attachments, and RN's custom monthly rule are shown read-only. Save sends only the changed draft fields, each with the value it was loaded with, and closes without a call when nothing changed; typed context, tag, and person text waits until core has said which draft value it stands for. If another writer changed a field you edited, core refuses the save, the draft stays, and **Try again** takes the stored value of each changed field while keeping your other edits. A failed or timed-out save locks the draft to its exact retry, like a failed capture. Leaving with unsaved edits asks Discard / Save / Cancel, as the mobile editor does. Typed text core has not resolved counts as an unsaved edit. Choosing Waiting first asks who or what it waits for, as RN does. The draft (its edits with the values they were loaded with, and the typed text) is kept in a synced file in the app's no-backup folder; saved instance state holds only that file's key. After process death core's model is read again and the draft goes on top, so a save still detects another writer's change. A save's exact request is written to that file before the call; if the process dies before core answers, the relaunch sends it again before the draft unlocks, and core writes nothing twice.

The **Focus** tab shows core's `getFocus` reply as it is: core's sections in core's order, with core's titles and totals, and each section's first 50 rows. **More** reads that section's next window through `getFocusSectionWindow`. Kotlin holds no Focus rules: it never sorts, filters, or groups rows, and it never reads a date. It uses only two row flags from core. A **Later today** heading goes before the first row core marks `laterToday`, and an Upcoming row shows core's `revealLabel` text as it is. Above the sections is core's date line (`dateLabel`) with RN's Focus only / Expand sections button. A section core counts as empty is not drawn, and "Projects to review" follows the task sections when core lists any. A tap on a section title folds it; which sections are open is kept on the device under RN's key `mindwtr:view:focus:v1`, in RN's JSON. Each row has RN's star (core's `setTaskFocus`; drawn disabled with core's `focusBlockedLabel` where the section sends one, as on Upcoming); a review-due row also has RN's status badge. Focus changes with the clock, so the app reads it again from the first row when the screen resumes, once a minute while Focus is on screen, and after every command. A refresh keeps each section as deep as More left it. If Focus changed before a More (core answers `STALE_REVISION`), the app reads Focus again from the first row; this is not an error. Complete (core's **Done** label) and the editor work from Focus exactly as from the Inbox, with the same exact-retry lock after a failure. Save and Cancel return to the tab the editor was opened from. The selected tab survives rotation and process death. A failed command's retry keeps its tab and rows, so a new screen reopens on Focus if the failure happened there.

The **Projects** tab starts with RN's **Add new project…** field: + (or Done on the keyboard) runs core's `createProject` with the area chosen on RN's area chips (by default the one area the filter selects). The draft, its area, and its request UUID survive process death; a failed create keeps its exact retry, and after process death the draft comes back but nothing is sent until + is tapped again. Then core's `getProjects` groups as they come: Active, then Someday / Waiting and Closed, which start closed and open on a tap, as on mobile. Each area header is core's area name (**No area** without one) with RN's colored dot and chevron, and folds its projects. Open groups and folded areas are kept on the device under RN's key `mindwtr:view:projects:v1`. A row shows the title, core's next action, its "No next action" warning, or core's status line, then core's active task count and RN's star (core's `setProjectFocus`, dimmed and disabled when five projects are starred). Tapping a project opens core's `getProjectDetail`: section markers and task rows in core's order, core's sequence cue under a row, and **More** for the next window. If the project changed between windows (core answers `STALE_REVISION`), the app reads it again from the first item. A row opens the editor and swipes to Done, except in an archived (read-only) project, whose rows have no swipe and a disabled status badge, as mobile does. Back returns to the list. The open project survives rotation and process death, and it is read again on every resume and after every command. A failed Done in a project keeps its exact retry, as on the other lists.

While a command's retry is owed, every screen's failure message offers **Try again**, which sends that exact request again, so a command started where its control is gone (a status change from the menu on Focus) stays retryable.

Reads the app starts on its own (on resume, each minute, and after every command) never disable a control, so a tap during one still runs; the engine thread queues both. Each read takes a number, and a command outdates every read that started before it, so an older result is never shown over a newer one.

Debug builds read three fault properties before each create, complete, or update command, and one language property at boot; release builds never read them:

- `debug.mindwtr.native.fail_commit=1` makes every SQLite `COMMIT` fail.
- `debug.mindwtr.native.delay_before_ms=<ms>` holds the command before it runs.
- `debug.mindwtr.native.delay_after_ms=<ms>` holds the acknowledgment after the commit.
- `debug.mindwtr.native.language=<code>` replaces the saved language (for example `zh`) for the next process, so a check never changes the phone's language.

`node apps/android-native/scripts/check-lifecycle-device.mjs <adb-serial>` uses these to check capture through rotation, process death, force-stop, and a failed commit that survives rotation, Back, and a new screen. It refuses any APK whose package is not the development package (checked with `aapt2`). It installs with `install -r`, keeps existing development data, and asserts on task titles unique to each run. Leave the device on its home screen first; the script stops (exit 3) rather than type into another app. It needs host `sqlite3`.

`node apps/android-native/scripts/check-editor-device.mjs <adb-serial>` checks the editor the same way: a save that changes the title, the due date, and a typed context; clearing a due date; a draft kept through rotation and through process death; a failed commit that keeps its exact retry through rotation, Back, and a new screen; a context chosen from core's suggestions and a due date with a time, in one save; and status Reference (core clears the due date) with a project from the Destination picker. It has the same install, safety, and exit-code rules as the lifecycle check.

`node apps/android-native/scripts/check-focus-device.mjs <adb-serial>` checks Focus the same way: two captured tasks set to Next appear under **Next actions**; a due date of today, picked on the day the picker marks as today, moves one under **Today**; Done from Focus stores `done` once; rotation and process death keep the Focus tab; the star moves a row under Today's Focus and back, stored once each; a failed Done keeps its exact retry through rotation, Back, and a new screen; and, on a fresh process after the relaunch, More adds rows to a section with more than 50 rows (the step is skipped when the development data has no such section). It has the same install, safety, and exit-code rules, and it leaves the app on its Inbox tab.

`node apps/android-native/scripts/check-projects-device.mjs <adb-serial> [--prune-old]` checks the Projects tab. The fixture needs sections and an archived project, which the app cannot make, so the script stops the app and, through core's own store on a host copy of the database, prepares one fixture found by stable titles: a sequential project with two sections, an archived project, and a project with 55 tasks. The first run injects it; later runs reuse it and only set its sequential tasks back to Next, so the development data does not grow. `--prune-old` also deletes, through core, the per-run projects and areas that earlier versions of this check injected. It then compares the screen with core's own replies on fresh copies: counts and next actions on the list, section markers, rows, and sequence cues in a project, Done stored once, the editor from a project, rotation and process death keeping the open project, a failed Done keeping its exact retry through rotation, Back, and a new screen, Back to the list, the read-only archived project, More, the project star, **Add new project…** into the fixture area (the next run's preparation deletes that project and resets the area filter and the fixture's stars through core), and the area switcher narrowing and widening the list as core does. It needs host `sqlite3` and `bun`.

`node apps/android-native/scripts/check-language-device.mjs <adb-serial>` checks that the tabs, the capture button, and the Inbox's "All areas" line show core's English, then core's Chinese with `debug.mindwtr.native.language=zh` in a fresh process, then English again.

`node apps/android-native/scripts/check-capture-device.mjs <adb-serial>` checks the capture popup against core's own quick capture on a database copy: a capture with a context and a tag stored exactly as core stores it, Add another (read from the switch's checkable node), a project picked in More's picker (created through the picker's Create row on the first run, as `5600`), two lines pasted through the field's real Paste (the debug build puts them on the clipboard from `debug.mindwtr.native.clipboard`; Enter saves, as in RN) with core's question and recovery snapshot (the file parses and holds the tasks the data had before the batch; one task per line, one write), a refused date command, and a failed commit's Try again. It leaves Add another off. It needs host `bun`.

`node apps/android-native/scripts/check-search-device.mjs <adb-serial>` checks global search against core's `searchTasks` on a database copy: a unique capture is found, the Inbox status filter and its active chip, the editor from a result, Mark Done, and Save Search for one fixed query (later runs add none). It needs host `bun`.

`node apps/android-native/scripts/check-process-inbox-device.mjs <adb-serial>` checks Process Inbox against core's own session on a database copy: the button's count, the first item and question, Yes and Back, rotation, and quick mode. Only when core's first item is a device check's own capture does it also trash it through a failed commit and its exact retry, and check process death before the write, after the write, and during the replay (the app lands on the Inbox, the item is stored at most once, and the record on disk goes only after core answers). It restores the phone's mode. It needs host `bun`.

The device checks type digits through the phone's own keyboard and never change its settings. Before launching and before any typing they read the current keyboard layout from `dumpsys input_method`; unless it is English (a Chinese Pinyin layout holds or reorders typed digits), or when the layout cannot be read, they stop with exit 3 and ask you to switch it with the globe key. `MINDWTR_KEYBOARD_OK=1` skips this after you have checked the keyboard yourself.

The lifecycle check proves each owed capture was sent again exactly once (one task carries the capture UUID it read from the no-backup file before the relaunch), scrolls the landscape popup to Save, and checks that the landscape Inbox shows at least three full task rows once its Process Inbox button scrolls away. The checks read the Inbox count from that button's spoken label (0 for RN's empty Inbox). All device checks clear the language property first, so they expect the phone's language to resolve to English.

Rotation and process death are validated only for this development identity, not for a production identity.

The `upgradetest` build type (`./gradlew :app:assembleUpgradetest`) is for the upgrade harness only. It installs as the throwaway package `tech.dongdongbh.mindwtr.upgradetest` over a real RN v1.3.2 build and opens the RN database, `files/SQLite/mindwtr.db`. Before anything opens that file, a guard refuses to start when the database is missing while other RN state exists and RN AsyncStorage (`databases/RKStorage`) holds no JSON backup, when that backup is over 64 MB, or when either file cannot be read or the database fails `quick_check`. The guard reads byte copies in the cache folder, never the files themselves. On a refusal the app shows the refusal message and changes no file. Otherwise the JS host imports the backup as RN's next launch would (core `planLegacyJsonImport`: the `mindwtr-data:json-ahead-of-sqlite` marker, the one-time reconcile, or an empty or missing database). After the import is saved and read back with every field equal, the guard copies `RKStorage` once to `files/SQLite/RKStorage.prewrite/`, then deletes the marker and/or sets the reconcile flag in one transaction. If either step fails, the app shows the failure message and makes no native write; the next boot retries only the `RKStorage` change. `node scripts/build-upgrade-harness.mjs` builds and signs the three harness APKs; `node scripts/check-upgrade-device.mjs <adb-serial>` runs the upgrade, JSON-backup import, damaged-database, missing-database and RN recovery scenarios on a phone. See the Harness section of `docs/development/native-android-upgrade-inventory.md`. `node scripts/capture-parity-screens.mjs <adb-serial>` uses the same harness APKs to shoot Inbox, Focus, Projects, one task's editor, global search, and Process Inbox's first step in light and dark mode, first in RN 154 and then in the native build, on one fixture database built through core, and writes side-by-side PNGs (RN left) to `/home/dd/.mindwtr-harness/parity/<timestamp>/`.
